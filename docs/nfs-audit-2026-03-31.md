**Finding:** DSM has no NFS rules configured for any share. The NFS mounts work because DSM NFS service is enabled globally (`enable_nfs=true`, `enable_nfs_v4=true`) and Proxmox mounts without share-level access control — any host on the network can mount any share.

## Risks

### RISK-1 — NFS with no access control (HIGH)
**Issue:** NFS service enabled with no per-share host restrictions. Any host on the 10.6.224.x/10.6.225.x network can mount `poc-iso` or `poc-backup`.
**Impact:** Compromised PoC VM → access to backup share → backup data readable/writable/deletable.
**Mitigation:** Add NFS rules per share, restricting to Proxmox node IP only (10.6.224.105).

### RISK-2 — Backup share writable by PoC (MEDIUM)
**Issue:** `poc-backup` is NFS-mounted with no root squash defined (default behavior unknown without explicit rule).
**Impact:** PoC automation error or runaway Terraform destroy could delete backup files.
**Mitigation:** Add NFS rule: host=10.6.224.105, rw=true, root_squash=true.

### RISK-3 — Legacy shares not cleaned up (LOW)
**Issue:** `proxmox`, `vm-backup`, `vm-images` exist with Proxmox-related descriptions but are not mounted anywhere. No NFS rules. Dead shares.
**Impact:** Confusion, audit noise.
**Mitigation:** Confirm unused → delete or rename to `ARCHIVE_*`.

## Decision for D3

**No cross-env NFS exposure found.** PoC only mounts PoC-dedicated shares. No shared folders between PoC and prod Proxmox were found — the concern in infra#50 is addressed.

The real risk is the absence of NFS access control rules, not env mixing.

**Recommendation:** D3 can be closed as "no prod/PoC sharing found — risk is uncontrolled NFS access, not env isolation."
